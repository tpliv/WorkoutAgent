## Key Question 1: Per-app profile (platforms, price, program builder, import, export, progression automation, any-order/rotation, watch, offline, data ownership)

### Takeaway
Only two candidates offer a programmatic path for an agent to push a program into the app: **Liftosaur** (text-based Liftoscript programs, shareable as text snippets or links; open-source AGPL; has an API behind Premium) and **Hevy** (official REST API with routine/routine-folder create/update endpoints, Pro-only). Everything else requires manual program entry; **Boostcamp** adds a web program builder plus shareable program links, and **Strong**, **Alpha Progression**, **FitNotes** offer CSV export for analysis but no import of custom programs.

## Key Question 2: Which apps have a public/documented API or an import format an agent could generate from markdown/CSV? Format details

### Takeaway
Liftosaur's Liftoscript is a plain-text program format (exercise lines with `sets x reps`, weights/`%`/`@RPE`, and `progress:` rules such as `lp()`, `dp()`, `sum()`, `custom()`) that can be shared as text or link and pasted into the app, making it the most direct markdown->program target; Hevy's Pro-only REST API (`api-key` header) supports creating/updating routines and routine folders programmatically.

### Cited Findings
- Liftoscript: omit weight and the app estimates from RPE tables (no RPE assumes failure at RPE 10; 12 reps ≈ 65% 1RM) — [Liftosaur docs](https://www.liftosaur.com/docs)
- Per-set targets: RPE `@8`, percentage of 1RM `80%`, or absolute `kg`/`lb`; set groups like `1x5 @8, 1x3 @9, 1x1 @10, 5x5 50%`; `+` after RPE logs actual RPE; `?+` asks for the weight after the fact — [Liftoscript doc](https://www.liftosaur.com/doc/liftoscript)
- `progress:` attaches a rule to an exercise, e.g. `progress: lp(5lb)` (linear progression) — [api3.liftosaur.com "How it works"](https://api3.liftosaur.com)
- New program editor: `progress: custom() { ... }` with Liftoscript in `{~ ~}` blocks, built-in variables like `weights` updated directly; warmup percentages are of the first set's weight, not 1RM — [Liftosaur blog: new program editor](https://www.liftosaur.com/blog/posts/new-experimental-program-editor)
- Progression types listed by third parties: `lp`, `dp`, `sum`, `custom`; `dp(weight, minReps, maxReps)` and `sum(totalReps, weight)` signatures appear in a fallback doc embedded in a community MCP server — [agentskills.so Liftosaur program creator skill](https://agentskills.so/skills/pbantolas-liftosaur-program-creator-liftosaur-program-creator); [Hugging Face liftosaur-mcp app.py](https://huggingface.co/spaces/davanstrien/liftosaur-mcp/blob/main/app.py) (signatures unverified against official docs)
- Programs can be shared as text snippets or links and pasted into the app; web editor available — [AppFollow listing](https://apps.appfollow.io/ios/liftosaur-scriptable-workouts/1661880849?country=td); [Liftosaur overview](https://www.liftosaur.com/blog/posts/liftosaur-overview/); link import confirmed in README — [GitHub README](https://github.com/astashov/liftosaur)
- Community tooling already exists for agents: a Liftosaur MCP server that fetches Liftoscript docs (overview, syntax, progressions) — [Hugging Face liftosaur-mcp](https://huggingface.co/spaces/davanstrien/liftosaur-mcp/blob/main/app.py); an agent "skill" for generating Liftosaur programs — [agentskills.so](https://agentskills.so/skills/pbantolas-liftosaur-program-creator-liftosaur-program-creator)
- Hevy API: REST, `api-key` header with per-account UUID; Pro-only; key from `https://hevy.com/settings?developer`; docs `https://api.hevyapp.com/docs/`; OpenAPI spec published (no standard security declaration) — [apis.io](https://apis.io/security/hevy/hevy-authentication/); [hevy-py](https://github.com/ewright3/hevy-py)
- Hevy API operations: create/update routines, create routine folders, list/create exercise templates, create/update workouts, workout events since timestamp, webhooks, exercise history — [hevy-py README](https://github.com/ewright3/hevy-py); community MCP server and CLI exist — [mcpmarket Hevy MCP](https://mcpmarket.com/server/hevy-5); [hevy-cli skill](https://skillsmp.com/creators/sajal2692/hevy-cli/skill-hevy-cli)
- Hevy CSV import accepts only Strong-format CSV (English), for workout history not routines — [Hevy help](https://help.hevyapp.com/hc/en-us/articles/38001424401943-How-to-Import-Strong-App-CSV-Files-and-Export-Your-Data-in-Hevy)
- Boostcamp: web program builder, programs saved appear in app, shareable by link — [Boostcamp custom program](https://boostcamp.app/custom-program); no API/file import found.
- Liftosaur API exists behind Premium with a personal API key (third-party claim) — [Wellness Project](https://wellnessproject.ai/fr/integrations/liftosaur) (unverified)

### Inferences
- An agent can deterministically render a markdown program into Liftoscript (one `Exercise / sets x reps @RPE or %` line per exercise plus a `progress:` rule) and commit it to the repo; the user pastes the text into Liftosaur or opens a generated share link. Double progression maps to `dp(...)`, linear to `lp(...)`, waves/percentages to explicit `%` per set with week structure, RPE to `@N+`.
- For Hevy, an agent script holding the user's Pro API key can create one routine per workout in the rotation inside a folder named for the program, and later pull workouts/exercise history as JSON for analysis — no CSV handling needed.
- Every other app requires the user to hand-enter the program; the agent can at best generate a printable/markdown checklist to speed manual entry.

### Gaps
- Official Liftoscript grammar for `dp`/`sum`, week/day block syntax and the share-link URL pattern (e.g. `/p/<id>`) could not be read from liftosaur.com (DNS failure); verify at https://www.liftosaur.com/docs before generating files.
- Hevy routine JSON field names (e.g. `weight_kg`, `reps`, `rpe`, `rest_seconds`) were not retrievable; consult https://api.hevyapp.com/docs/ directly.
- Whether Hevy's API exposes RPE per set, and API rate limits.

## Key Question 3: Best apps for "any-order rotation" programs and for RPE/RIR logging

### Takeaway
Hevy and Strong store programs as unscheduled routines/templates that the lifter starts in any order, and Liftosaur's scripted programs advance through a defined sequence regardless of calendar day; for RPE/RIR logging, Liftoscript has native `@RPE`/`+` logging, Boostcamp logs RPE and RIR free on every set, Strong supports RPE, and Alpha Progression gates RIR analysis behind Premium.

### Cited Findings
- Hevy routines are started by tapping "Start Routine" from the Workout tab; folders group routines by split; no weekday scheduling described — [Hevy help: Build a Workout Program](https://help.hevyapp.com/hc/en-us/articles/34953606698903-Build-a-Workout-Program-Create-Organize-Routines); [Hevy help: Log a Workout](https://help.hevyapp.com/hc/en-us/articles/35361530647959-How-to-Log-a-Workout-in-the-Hevy-App-Step-by-Step-Guide)
- Strong: RPE supported; custom routines (templates) with cap removed on PRO — [Boostcamp vs Strong](https://www.boostcamp.app/vs/strong) (competitor)
- Liftosaur: progression/deload logic runs "according to logic you define"; programs are sequences of days with `progress:` rules — [GitHub README](https://github.com/astashov/liftosaur); [api3.liftosaur.com](https://api3.liftosaur.com); RPE logging via `@8+` — [Liftoscript doc](https://www.liftosaur.com/doc/liftoscript)

## Addendum 2026-10-21: Hevy public API verified against the OpenAPI document

Last updated: 2026-10-21. The research sandbox for the main note could not open `api.hevyapp.com`. A later session could: `https://api.hevyapp.com/docs/` is a Swagger UI whose `swagger-ui-init.js` embeds the OpenAPI 3.0.0 document ("Hevy Public API Docs"). Everything below was read from that document, not from third-party SDKs, and resolves the gaps flagged in KQ2 and KQ5. Source: [Hevy API docs](https://api.hevyapp.com/docs/) (official, primary).

**Access and terms.** "Currently, this API is only available to Hevy Pro users. You can get your key on our web app at https://hevy.com/settings?developer." Hevy states it makes "no guarantees that we won't completely change the structure or abandon the project entirely", and asks clients that poll hourly or daily not to send requests exactly at xx:00. Authentication is an `api-key` header. No rate limit is documented. An unauthenticated request returns HTTP 401.

**Endpoints** (all under `/v1`):

| Method and path | Purpose | Notes |
|---|---|---|
| `GET /workouts` | Paginated workouts | `page`, `pageSize` (max 10); response `{page, page_count, workouts[]}` |
| `GET /workouts/count` | Total workouts | `{workout_count}` |
| `GET /workouts/events` | Updates and deletes since a timestamp | `since` (ISO 8601), newest first; events are `{type: "updated", workout}` or `{type: "deleted", id, deleted_at}`; intended for keeping a local cache current |
| `GET /workouts/{id}`, `POST /workouts`, `PUT /workouts/{id}` | Read, create, update a workout | Create requires `title, start_time, end_time, exercises`; `is_private` optional |
| `GET /user/info` | Account info | `{data: {...}}` |
| `GET /routines`, `GET /routines/{id}`, `POST /routines`, `PUT /routines/{id}` | Routines | `pageSize` max 10; POST returns 403 "Routine limit exceeded" on the free tier; PUT returns 404 if the routine is not the caller's |
| `GET /routine_folders`, `GET /routine_folders/{id}`, `POST /routine_folders` | Folders | New folder is created at index 0 |
| `GET /exercise_templates`, `GET /exercise_templates/{id}`, `POST /exercise_templates` | Exercise library | `pageSize` max 100; POST creates a custom exercise (`title, exercise_type, equipment_category, muscle_group, other_muscles`) |
| `GET /exercise_history/{templateId}` | Every logged set of one exercise | `start_date`, `end_date`; entries carry `workout_id, workout_title, workout_start_time, weight_kg, reps, rpe, set_type` |
| `GET/POST /body_measurements`, `GET/PUT /body_measurements/{date}` | Bodyweight and girths | `weight_kg, lean_mass_kg, fat_percent`, neck to calf in cm; POST returns 409 if the date exists |

**Not in the published document:** any delete endpoint for routines or folders, and any webhook endpoint. The hevy-py README's webhook claim (KQ2) is therefore unverified against the official spec as of this date; treat it as absent.

**Workout schema** (answers the per-set RPE gap in KQ2, KQ5 and chapter 07): `Workout {id, title, routine_id, description, start_time, end_time, updated_at, created_at, exercises[]}`; `exercises[] {index, title, notes, exercise_template_id, superset_id, sets[]}`; `sets[] {index, type, weight_kg, reps, distance_meters, duration_seconds, rpe, custom_metric}`. **`rpe` is a per-set, nullable number.** On `POST /workouts` it is an enum of 6, 7, 7.5, 8, 8.5, 9, 9.5, 10 (no 6.5). `type` is one of `normal`, `warmup`, `dropset`, `failure`. `weight_kg` is always kilograms whatever the app's display unit. `routine_id` links a workout to the routine it was started from.

**Routine schema** (answers the routine-field gap): `Routine {id, title, folder_id, updated_at, created_at, exercises[]}`; `exercises[] {index, title, rest_seconds, notes, exercise_template_id, superset_id, sets[]}`; `sets[] {index, type, weight_kg, reps, rep_range {start, end}, distance_meters, duration_seconds, custom_metric}`. **Routine sets have no RPE field**, so RPE targets must go in the exercise `notes`. Request bodies are `{routine: {title, folder_id, notes, exercises[{exercise_template_id, superset_id, rest_seconds, notes, sets[...]}]}}`; `folder_id: null` puts the routine in "My Routines".

**Exercise templates:** `{id, title, type, primary_muscle_group, secondary_muscle_groups[], equipment, is_custom, thumbnail_url}`. Built-in titles follow the pattern seen in the user's export ("Bench Press (Barbell)", "Squat (Barbell)", "Lat Pulldown (Cable)"). Custom exercise types: `weight_reps, reps_only, bodyweight_reps, bodyweight_assisted_reps, duration, weight_duration, distance_duration, short_distance_weight`. Equipment: `none, barbell, dumbbell, kettlebell, machine, plate, resistance_band, suspension, other`. Muscle groups: 20 values from `abdominals` to `other`.

**Consequences for this repo** (inference): the agent-driven loop in chapter 07 section 3.2 is fully supported: push nine routines into a folder (`POST /routine_folders`, `POST /routines`), update loads weekly (`PUT /routines/{id}`), read history with RPE (`GET /workouts` or `/workouts/events?since=`), and read bodyweight (`GET /body_measurements`). The only missing pieces are webhooks (poll instead) and routine deletion (delete in the app). Implemented in `tools/hevy_api.py`, `hevy_pull.py`, `hevy_push_routines.py`, `update_tracks.py` and `hevy_sync.py`.

**Observed on the live API (2026-10-21, first push to the user's account):** `POST /routine_folders` returns `{"routine_folder": {...}}`, not the bare `RoutineFolder` the spec shows; `GET /routines/{id}` likewise wraps as `{"routine": {...}}`. `GET /user/info` returns `weight_unit` ("lbs" on this account) while every API weight stays in kg. Exercise titles that differ from guesses: "Seated Incline Curl (Dumbbell)", "Cable Core Pallof Press", "EZ Bar Biceps Curl", "Hack Squat (Machine)", "Pull Up (Weighted)". The tools accept both response shapes.

**Still unverified:** rate limits (none documented); whether `pageSize` above the maximum returns 400 as documented; the exact built-in titles for exercises the user has not logged yet (the push tool tries a list of candidates and reports what did not match).

### Corrections

### Liftoscript check of `templates/liftosaur/rotation.liftoscript`

Checked against the Liftoscript doc, the grammar file, and the built-in exercise list in `src/models/exercise.ts` (GitHub master, 2026-10-21). Not run through the parser; the playground endpoint would confirm.

- **Parse errors expected: trailing `//` text on every exercise line** (lines 31-36, 39-44, 47-52, 55-60, 63-68, 71-77). In the grammar, an exercise line is sections separated by `/` up to the line break. A trailing `// ...` reads as two more `/` separators followed by text that is not a valid section. Fix: move each note to its own `///` line above the exercise.
- **Error: conflicting progressions for one exercise.** Standing Calf Raise has `dp(2.5kg, 8, 12)` on lines 35 and 51 and `dp(2.5kg, 10, 15)` on line 67. The doc says different progressions for the same exercise give an error. Fix: give line 67 a label (for example `c: Standing Calf Raise`) or use the same arguments.
- **Unknown exercise names** (the API's example error is "Unknown exercise: ..."), unless you create custom exercises with these exact names: line 41 `Incline Dumbbell Press` (built-in: `Incline Bench Press, Dumbbell`), lines 42 and 75 `Dumbbell Lateral Raise` (`Lateral Raise`, default dumbbell), line 43 `Overhead Cable Triceps Extension` (`Triceps Extension, Cable`), line 49 `Walking Lunge` (`Lunge, Dumbbell`), line 57 `Dumbbell Bench Press` (`Bench Press, Dumbbell`), line 58 `Reverse Pec Deck` (`Reverse Fly, Leverage Machine`), line 59 `Cable Lateral Raise` (`Lateral Raise, Cable`), line 60 `Incline Dumbbell Curl` (`Incline Curl`, dumbbell only). All other names match the library.
- **Semantic problem: the V lines are not isolated.** Lines 63, 64, 71, 72, 73 and 74 have no progress rule "on purpose", but a progression applies to every instance of the exercise in the program. So the V sessions inherit `lp(2.5kg)`, `lp(1kg)` or `dp(...)` from the H lines and can advance the shared track. Line 73 (row `3x8-10`) also inherits `dp(2.5kg, 6, 8)`, which does not match its range. Fix: add `/ progress: none` to those lines, or label them (`v: Squat`).
- **Cosmetic:** line 28's trailing text becomes part of the week name (the `#` header runs to the end of the line). Lines 1-26 sit above `# Week 1`, so they show to the lifter as the week description. Lines 79-81 are descriptions with no exercise after them. Use `///` for all three.
- **Fine as written:** `# Week 1` / `## Day N: ...` headers, `1x4 120kg @8+, 3x4 112.5kg @7+` (weight and logged RPE per set group), `3x8-10 @8+`, `lp(2.5kg)`, `lp(1kg)`, `dp(2kg, 8, 12)`, `Pull Up / 4x5-8 10kg @8+` (it parses; for the number to mean added load, turn on "Bodyweight for Bar", optionally writing `Pull Up, Bodyweight`). Accessory lines without a weight get a weight estimated from the RPE target and the exercise's 1RM.

### Addendum 2026-10-21 (later): local parser run of the Liftosaur export

Method: Liftosaur's open-source code (GitHub master, 2026-10-21) was run locally: the generated planner parser and the validation and day-simulation functions behind `POST /api/v1/playground`. The hosted playground needs a Premium key and was not called. Findings (observed behaviour, not documented in official text):

- The rewritten `templates/liftosaur/rotation.liftoscript` parses and validates with no errors. Finishing each simulated day moved the expected weights and left the labelled V lines unchanged.
- `dp()` on sets written as a rep range (`3x8-10`) collapsed the range to 10-10 after a run. The file writes the bottom of the range (`3x8 ... dp(2.5kg, 8, 10)`) instead.
- `progress: none` on a copy of an exercise did not stop an `lp()` step elsewhere from rewriting that copy's weights. Labels (`v: Squat`) isolate the V copies; `progress: none` alone does not.
